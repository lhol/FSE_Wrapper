## Issue 1 — Maven publishing merged into `release.yaml`, kept optional

### Background
`release-maven.yaml` triggers independently on the same `v*.*.*` tag as
`release.yaml`.  Both workflows gate on the `release` environment (approval
step).  The user wants a single approval gate and Maven publishing to live
inside `release.yaml` just like NuGet, but remain skippable.

### Decisions
- Maven publishing lives in a new `maven-publish` job inside `release.yaml`,
  positioned after `release` (same as `nuget-publish`).
- The job uses `environment: release` and `continue-on-error: true`.
- `release-maven.yaml` is **deleted** (superseded).
- Native artifacts for all platforms are downloaded so the deployed JAR contains
  native libs for all targets (see also Issue 6).
- A companion `smoke-maven` job is added (see Issue 3).

### Changes
| File | Change |
|------|--------|
| `.github/workflows/release.yaml` | Add `maven-publish` job + `smoke-maven` job |
| `.github/workflows/release-maven.yaml` | Delete file |

### `maven-publish` job skeleton (add after `nuget-publish`)
```yaml
maven-publish:
  needs: release
  runs-on: ubuntu-latest
  environment: release
  continue-on-error: true
  steps:
    - uses: actions/checkout@v5
      with:
        submodules: recursive
    - uses: actions/setup-java@v5
      with:
        distribution: temurin
        java-version: '22'
        cache: maven
        server-id: central
        server-username: CENTRAL_TOKEN_USERNAME
        server-password: CENTRAL_TOKEN_PASSWORD
        gpg-private-key: ${{ secrets.GPG_PRIVATE_KEY }}
        gpg-passphrase: MAVEN_GPG_PASSPHRASE
    - name: Download all native artifacts
      uses: actions/download-artifact@v5
      with:
        pattern: native-*-${{ github.ref_name }}
        merge-multiple: true
        path: native/build
    - name: Set version from tag
      run: |
        VERSION=$(echo "${{ github.ref_name }}" | sed 's/^v//')
        ./mvnw versions:set -DnewVersion=${VERSION} -DgenerateBackupPoms=false
        ./mvnw -f java-panama/pom.xml versions:set -DnewVersion=${VERSION} \
               -DgenerateBackupPoms=false
    - name: Deploy JNI JAR to Maven Central
      env:
        CENTRAL_TOKEN_USERNAME: ${{ secrets.CENTRAL_TOKEN_USERNAME }}
        CENTRAL_TOKEN_PASSWORD: ${{ secrets.CENTRAL_TOKEN_PASSWORD }}
        MAVEN_GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}
      run: |
        ./mvnw -B clean deploy -DskipTests \
          -Dgpg.passphrase="${{ secrets.GPG_PASSPHRASE }}"
    - name: Deploy Panama JAR to Maven Central
      env:
        CENTRAL_TOKEN_USERNAME: ${{ secrets.CENTRAL_TOKEN_USERNAME }}
        CENTRAL_TOKEN_PASSWORD: ${{ secrets.CENTRAL_TOKEN_PASSWORD }}
        MAVEN_GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}
      run: |
        ./mvnw -f java-panama/pom.xml -B clean deploy -DskipTests \
          -Dgpg.passphrase="${{ secrets.GPG_PASSPHRASE }}"
```

### Acceptance criteria
- Pushing a `v*.*.*` tag triggers one workflow, one approval gate.
- Skipping the approval still lets zip files upload to the GitHub Release.
- `release-maven.yaml` no longer exists in the repo.

## Issue 2 — NuGet smoke test: 15-minute propagation delay

### Background
NuGet.org has eventual-consistency latency: a freshly pushed package can take
several minutes to appear in search.  The `smoke-nuget` job fails with
`NU1102: Unable to find package … with version (>= X.Y.Z)`.

### Change
In `release.yaml`, inside the `smoke-nuget` job, add a wait step **before**
`dotnet add package`:

```yaml
- name: Wait for NuGet propagation (15 min)
  run: sleep 900
```

The job already carries `continue-on-error: true`, so a remaining flake won't
block the release.

### Files
| File | Change |
|------|--------|

### Acceptance criteria
- `smoke-nuget` consistently resolves the newly published package version.
- If it still fails (e.g., extended outage), the release is not blocked.

## Issue 3 — Maven smoke test (new job)

### Background
No smoke test exists for the Maven Central artifacts.  After publishing, a
minimal Java project should install the JNI and Panama JARs and run a
compress/decompress round-trip, mirroring the NuGet smoke test.

### New job: `smoke-maven` (in `release.yaml`)
```yaml
smoke-maven:
  needs: maven-publish
  runs-on: ubuntu-latest
  continue-on-error: true
  steps:
    - name: Wait for Maven Central propagation (15 min)
      run: sleep 900
    - uses: actions/setup-java@v5
      with:
        distribution: temurin
        java-version: '22'
    - name: Create and test minimal Maven consumer
      run: |
        VERSION=$(echo "${{ github.ref_name }}" | sed 's/^v//')
        mkdir -p /tmp/smoke-maven/src/main/java/smoke
        cd /tmp/smoke-maven
        cat > pom.xml << EOF
        <project>
          <modelVersion>4.0.0</modelVersion>
          <groupId>smoke</groupId><artifactId>smoke</artifactId><version>1.0</version>
          <dependencies>
            <dependency>
              <groupId>io.github.lhol</groupId>
              <artifactId>FSE_Wrapper</artifactId>
              <version>${VERSION}</version>
            </dependency>
          </dependencies>
          <build><plugins>
            <plugin>
              <groupId>org.codehaus.mojo</groupId>
              <artifactId>exec-maven-plugin</artifactId>
              <version>3.1.0</version>
            </plugin>
          </plugins></build>
        </project>
        EOF
        cat > src/main/java/smoke/SmokeTest.java << 'JAVA'
        package smoke;
        import io.github.lhol.huff0.Huff0;
        import io.github.lhol.fse.Fse;
        import java.nio.charset.StandardCharsets;
        import java.util.Arrays;
        public class SmokeTest {
            public static void main(String[] args) throws Exception {
                byte[] data = "Hello from FSE_Wrapper Maven smoke test!".getBytes(StandardCharsets.UTF_8);
                byte[] h0c  = Huff0.compress(data);
                byte[] h0d  = Huff0.decompress(h0c, data.length);
                if (!Arrays.equals(data, h0d)) throw new RuntimeException("Huff0 roundtrip failed");
                byte[] fsec = Fse.compress(data);
                byte[] fsed = Fse.decompress(fsec, data.length);
                if (!Arrays.equals(data, fsed)) throw new RuntimeException("FSE roundtrip failed");
                System.out.println("Smoke test passed: Huff0 and FSE roundtrip OK");
            }
        }
        JAVA
        mvn -q compile exec:java -Dexec.mainClass=smoke.SmokeTest
```

| File | Change |
|------|--------|
| `.github/workflows/release.yaml` | Add `smoke-maven` job after `maven-publish` |

### Acceptance criteria
- `smoke-maven` succeeds after a release where Maven Central publishing worked.
- Failure does not block the release.
- Same round-trip pattern as `smoke-nuget`.

## Issue 4 — `bench` job picks javadoc JAR instead of shaded fat JAR

### Root cause
```bash
JAR=$(ls target/FSE_Wrapper-*.jar | grep -v original | head -1)
```
After `mvn package`, several JARs are created:
- `FSE_Wrapper-X.Y.Z.jar` (shaded fat JAR, has `Main-Class: org.openjdk.jmh.Main`)
- `FSE_Wrapper-X.Y.Z-javadoc.jar`
- `FSE_Wrapper-X.Y.Z-sources.jar`

Alphabetically `FSE_Wrapper-0.1.1-javadoc.jar` sorts before
`FSE_Wrapper-0.1.1.jar`, so `head -1` selects the javadoc JAR →
`no main manifest attribute`.

### Fix
In **both** `release.yaml` (bench job) and `rc.yaml` (bench job), change the
JAR selection line to:

```bash
JAR=$(ls target/FSE_Wrapper-*.jar | grep -v original | grep -v '\-javadoc' | grep -v '\-sources' | head -1)
```

### Files
| File | Change |
|------|--------|
| `.github/workflows/release.yaml` | Fix JAR selection in `bench` job |
| `.github/workflows/rc.yaml` | Fix JAR selection in `bench` job |

### Acceptance criteria
- The `bench` job selects the shaded fat JAR and runs JMH benchmarks without
  the `no main manifest attribute` error.

## Issue 5 — Remove JMH from published Maven library JARs

### Background
JMH is declared as a compile-scope dependency, so it is shaded into the fat JAR
that gets published to Maven Central.  This inflates the JAR significantly and
generates ~78 Javadoc warnings from the JMH annotation-processor generated
sources.

### Plan

#### 5a — Scope JMH as `provided` for the library build, `compile` only for the bench fat JAR

Create two Maven profiles in `pom.xml`:

- **Default profile (no `-P` flag)**: JMH in `provided` scope; maven-shade
  produces a *library* JAR containing only the `io.github.lhol.*` classes and
  embedded native libs.  No `Main-Class` manifest attribute.  This is what
  Maven Central receives.
- **`bench` profile (`-P bench`)**: JMH in `compile` scope; maven-shade sets
  `Main-Class: org.openjdk.jmh.Main` and includes JMH.  Used only by the
  CI `bench` jobs and local benchmarking.

#### 5b — Suppress JMH Javadoc warnings

Add `<doclint>none</doclint>` to the `maven-javadoc-plugin` configuration so
that missing-comment warnings from JMH-generated sources do not appear in the
build log.

#### 5c — Exclude JMH source dir from library compilation

With `build-helper-maven-plugin`, add the `java/src/jmh/java` source path only
when the `bench` profile is active.

#### pom.xml changes (summary)

```xml
<!-- JMH: provided by default, compile in bench profile -->
<dependency>
  <groupId>org.openjdk.jmh</groupId>
  <artifactId>jmh-core</artifactId>
  <version>1.37</version>
  <scope>provided</scope>      <!-- changed from compile -->
</dependency>
<dependency>
  <groupId>org.openjdk.jmh</groupId>
  <artifactId>jmh-generator-annprocess</artifactId>
  <version>1.37</version>
  <scope>provided</scope>
</dependency>

<!-- maven-javadoc-plugin: suppress doclint warnings -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-javadoc-plugin</artifactId>
  <configuration>
    <source>11</source>
    <doclint>none</doclint>    <!-- suppress JMH-generated warnings -->
  </configuration>
</plugin>

<!-- bench profile -->
<profile>
  <id>bench</id>
  <dependencies>
    <dependency>
      <groupId>org.openjdk.jmh</groupId>
      <artifactId>jmh-core</artifactId>
      <version>1.37</version>
      <scope>compile</scope>
    </dependency>
    <dependency>
      <groupId>org.openjdk.jmh</groupId>
      <artifactId>jmh-generator-annprocess</artifactId>
      <version>1.37</version>
      <scope>provided</scope>
    </dependency>
  </dependencies>
  <build>
    <plugins>
      <!-- Re-add JMH source dir -->
      <plugin>
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>build-helper-maven-plugin</artifactId>
        <version>3.6.0</version>
        <executions>
          <execution>
            <phase>generate-sources</phase>
            <goals><goal>add-source</goal></goals>
            <configuration>
              <sources><source>java/src/jmh/java</source></sources>
            </configuration>
          </execution>
        </executions>
      </plugin>
      <!-- Shade plugin with JMH Main-Class, only for bench -->
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-shade-plugin</artifactId>
        <version>3.5.0</version>
        <executions>
          <execution>
            <phase>package</phase>
            <goals><goal>shade</goal></goals>
            <configuration>
              <shadedArtifactAttached>true</shadedArtifactAttached>
              <shadedClassifierName>benchmarks</shadedClassifierName>
              <transformers>
                <transformer implementation="...ManifestResourceTransformer">
                  <mainClass>org.openjdk.jmh.Main</mainClass>
                </transformer>
                <transformer implementation="...AppendingTransformer">
                  <resource>META-INF/BenchmarkList</resource>
                </transformer>
                <transformer implementation="...AppendingTransformer">
                  <resource>META-INF/CompilerHints</resource>
                </transformer>
                <transformer implementation="...ServicesResourceTransformer"/>
              </transformers>
            </configuration>

        </executions>
      </plugin>
    </plugins>
  </build>
```

## Issue 6 — Native binaries missing from Maven-published JARs (extended)

### Background and root-cause analysis

**Three separate problems compound here:**

1. **No native libs at all in the published JAR.**  
   The Maven workflow only downloads `linux-x64` (with `continue-on-error: true`),
   so the other four platform libs are absent.

2. **Flat merge causes silent file clobber.**  
   If all artifacts were merged into one flat directory, both `linux-x64` and
   `linux-arm64` produce `libhuff0.so`; both `win-x64` and `win-arm64` produce
   `huff0.dll`. The second copy silently overwrites the first — four out of
   five platforms end up wrong.

3. **No runtime extraction: the `natives/` folder in the JAR is never used.**  
   Both `Huff0.java` and `Fse.java` call `System.loadLibrary("huff0")`, which
   searches `java.library.path` only — it cannot reach inside a JAR.  The
   bundled natives are dead weight unless a `NativeLoader` extracts them first.

### Why subdirectories — not arch-in-filename

The user's instinct is correct: **putting the CPU type in the DLL name makes
calling code harder to write and is not the standard approach**.

`[DllImport("huff0")]` is a C# compile-time constant; you cannot choose
`"huff0_x64"` vs `"huff0_arm64"` at runtime without rewriting the interop
layer.  `System.loadLibrary("huff0")` has the same constraint — the OS
resolves the bare name `"huff0"` to `libhuff0.so` / `huff0.dll` itself.

The standard solution, used by virtually every multi-platform Java native
library (sqlite-jdbc, netty, leveldbjni, bytedeco, …) is:

```
natives/{rid}/{os-native-libname}
```

Where `{rid}` is a runtime-identifier string (same concept as the NuGet RID):

```
natives/linux-x64/libhuff0.so
natives/linux-arm64/libhuff0.so
natives/osx-arm64/libhuff0.dylib
natives/win-x64/huff0.dll
natives/win-arm64/huff0.dll
```

Each file keeps its canonical OS name (`huff0.dll`, `libhuff0.so`) — no
naming conflict, no change to the DllImport/loadLibrary call.  A small
`NativeLoader` utility selects the correct subdirectory at runtime.

NuGet already uses exactly this pattern (`runtimes/{rid}/native/`) and
handles dispatch automatically — no C# code changes are needed at all.

### Implementation plan

#### 6a — Per-platform subdirectory layout in `native/artifacts/`

Change the CI artifact staging from a single flat `native/build` directory to
per-RID subdirectories.  In the `maven-publish` job (from Issue 1), replace
the single `download-artifact` step with five separate downloads:

```yaml
- name: Download native artifacts per platform
  run: mkdir -p native/artifacts/{linux-x64,linux-arm64,osx-arm64,win-x64,win-arm64}
- uses: actions/download-artifact@v5
  with: { name: native-linux-x64-${{ github.ref_name }},   path: native/artifacts/linux-x64  }
- uses: actions/download-artifact@v5
  with: { name: native-linux-arm64-${{ github.ref_name }}, path: native/artifacts/linux-arm64 }
- uses: actions/download-artifact@v5
  with: { name: native-macos-arm64-${{ github.ref_name }}, path: native/artifacts/osx-arm64  }
- uses: actions/download-artifact@v5
  with: { name: native-win-x64-${{ github.ref_name }},     path: native/artifacts/win-x64    }
- uses: actions/download-artifact@v5
  with: { name: native-win-arm64-${{ github.ref_name }},   path: native/artifacts/win-arm64  }
```

> The same staging layout is reused for the `java-jni` multi-platform JAR
> (currently it uses `merge-multiple: true` and therefore has the same clobber

#### 6c — New `NativeLoader` utility class

Create `java/src/main/java/io/github/lhol/NativeLoader.java`:

```java
package io.github.lhol;

import java.io.*;
import java.nio.file.*;

/**
 * Extracts a platform-native shared library from the classpath (JAR) to a
 * temporary directory and loads it via {@link System#load}.
 *
 * <p>Library lookup order:
 * <ol>
 *   <li>{@code /natives/{rid}/{libname}} inside the JAR (multi-platform distribution)</li>
 *   <li>{@code /natives/local/{libname}} inside the JAR (local developer build)</li>
 *   <li>{@code System.loadLibrary(name)} — falls back to {@code java.library.path}</li>
 * </ol>
 */
public final class NativeLoader {

    private static final Path TEMP_DIR;

    static {
        try {
            TEMP_DIR = Files.createTempDirectory("fse-wrapper-");
            Runtime.getRuntime().addShutdownHook(new Thread(() -> {
                try { deleteRecursive(TEMP_DIR); } catch (IOException ignored) {}
            }));
        } catch (IOException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    private NativeLoader() {}

    /**
     * Loads the named native library, extracting it from the JAR if present.
     *
     * @param name bare library name, e.g. {@code "huff0"} (no prefix/suffix)
     */
    public static synchronized void load(String name) {
        String libFileName = mapLibName(name);
        String rid = detectRid();

        // Try bundled multi-platform path first, then local-build fallback
        for (String prefix : new String[]{"natives/" + rid, "natives/local"}) {
            String resourcePath = "/" + prefix + "/" + libFileName;
            try (InputStream in = NativeLoader.class.getResourceAsStream(resourcePath)) {
                if (in == null) continue;
                Path target = TEMP_DIR.resolve(rid + "_" + libFileName);
                if (!Files.exists(target)) {
                    Files.copy(in, target);
                }
                System.load(target.toAbsolutePath().toString());
                return;
            } catch (IOException e) {
                throw new UnsatisfiedLinkError(
                    "Failed to extract " + resourcePath + ": " + e.getMessage());
            }
        }

        // Final fallback: rely on java.library.path (e.g. running tests via surefire)
        System.loadLibrary(name);
    }

    /** Maps a bare name to the OS-specific filename. */
    static String mapLibName(String name) {
        String os = System.getProperty("os.name", "").toLowerCase();
        if (os.contains("win"))  return name + ".dll";
        if (os.contains("mac"))  return "lib" + name + ".dylib";
        return "lib" + name + ".so";   // Linux and others
    }

    /** Detects the current platform as a RID string. */
    static String detectRid() {
        String os   = System.getProperty("os.name", "").toLowerCase();
        String arch = System.getProperty("os.arch", "").toLowerCase();
        boolean arm = arch.contains("aarch64") || arch.contains("arm64");
        if (os.contains("linux")) return arm ? "linux-arm64" : "linux-x64";
        if (os.contains("mac"))   return "osx-arm64";
        if (os.contains("win"))   return arm ? "win-arm64"   : "win-x64";
        throw new UnsatisfiedLinkError("Unsupported platform: " + os + " / " + arch);
    }

    private static void deleteRecursive(Path path) throws IOException {
        if (!Files.exists(path)) return;
        try (var stream = Files.walk(path)) {
            stream.sorted(java.util.Comparator.reverseOrder())
                  .map(Path::toFile)
                  .forEach(File::delete);
        }
    }
}
```

#### 6d — Update `Huff0.java`, `Fse.java`, `Huff0Panama.java`, `FsePanama.java`

Replace the `System.loadLibrary(...)` call in each static initializer:

```java
// Before
static { System.loadLibrary("huff0"); }

// After
static { io.github.lhol.NativeLoader.load("huff0"); }
```

Apply to all four files:
- `java/src/main/java/io/github/lhol/huff0/Huff0.java`
- `java/src/main/java/io/github/lhol/fse/Fse.java`
- `java-panama/src/main/java/io/github/lhol/huff0/Huff0Panama.java`
- `java-panama/src/main/java/io/github/lhol/fse/FsePanama.java`

> `NativeLoader` lives in the `fse-wrapper` JNI JAR.  The Panama JAR
> depends on the JNI JAR, so it can reference `NativeLoader` directly.
> If the two JARs are kept independent, copy `NativeLoader` into
> `java-panama/src/main/java/io/github/lhol/` as well.

#### 6e — Developer workflow: local build path

When running tests locally, the native libs sit in `native/build` (or
`native/build/Release` on Windows).  The `natives/local/` resource entry
(added in 6b) and `NativeLoader`'s `local` fallback mean that
`./mvnw test` still works without staging the artifacts.  The existing
maven-surefire `-Djava.library.path` argument can be kept as a second-level
fallback for IDEs that launch tests outside Maven.

#### 6f — C# / NuGet — no changes required

The NuGet packages already use the correct RID structure
(`runtimes/win-x64/native/huff0.dll`, `runtimes/win-arm64/native/huff0.dll`).
The .csproj includes the whole `runtimes/**/*` tree.  The .NET runtime
selects the right DLL automatically — no change to `[DllImport("huff0")]`
is needed.

The only CI change for the `dotnet` job: make sure the per-RID downloads
that feed the `Populate NuGet runtimes directories` step are correct
(they already are — they use separate subdirectory downloads, not
`merge-multiple: true`).

## Issue 7 — Benchmark quirks

Four sub-issues, each with its own fix.

### 7a — Very big numbers for large data sizes

**Root cause**: `_fmt()` in `generate_dashboard.py` has an inverted condition:

```python
# current (buggy)
if val >= 1000:
    return f"{val/1000:.1f}GB/s" if val >= 1024*1024 else f"{val:.0f} MB/s"
```

`1024*1024` ≈ 1 million MB/s (≈ 1 TB/s) — never reached in practice.  Values
above 1000 MB/s are always shown without a decimal point ("5000 MB/s") which
looks unexpectedly large.

**Fix**:
```python
def _fmt(val):
    if val is None:
        return "—"
    if val >= 1000:
        return f"{val/1000:.1f} GB/s"
    return f"{val:.1f} MB/s"
```

### 7b — Medium entropy text block too short

The current `LOREM` constant in both `CodeBench.java` files is a single
paragraph (~460 bytes) of classic Lorem Ipsum.  For large data sizes it is
repeated, which creates artificial regularity that a real compressor would
exploit.

**Fix** — replace `LOREM` with a longer, mixed-content block (~4 KB) combining:
- Wikipedia-style prose text
- A block of digits / numbers
- Mixed punctuation and capitalization

This avoids trivial periodicity and makes the benchmark more representative.
Suggested source: a freely licensed passage from a Wikipedia article (e.g.,
the first three paragraphs of "Data compression").

Both files must be updated:
- `java/src/jmh/java/io/github/lhol/huff0/CodeBench.java`
- `java/src/jmh/java/io/github/lhol/fse/CodeBench.java`

### 7c — Java JNI / Panama / .NET columns always empty

**Root cause** — The dashboard script hard-codes method names that do not match
the actual JMH benchmark method names:

| Script expects | Actual JMH method |
|---|---|
| `huff0CompressJNI` | `huff0Compress` |
| `huff0CompressPanama` | *(no Panama benchmark yet)* |
| `fseCompressJNI` | `fseCompress` |
| `fseCompressPanama` | *(no Panama benchmark yet)* |

**Fix A** — Rename the JMH benchmark methods to match the dashboard:
- `huff0Compress` → `huff0CompressJNI` in `huff0/CodeBench.java`
- `fseCompress` → `fseCompressJNI` in `fse/CodeBench.java`
- Add Panama benchmarks `huff0CompressPanama` / `fseCompressPanama` in the
  `java-panama` module (new `CodeBench.java` file there).

**Fix B** — For .NET, audit whether BenchmarkDotNet writes to the expected
